# AGENTS.md — Регламент работы ИИ-агента

Этот репозиторий развивается по принципам надёжной и безопасной разработки.
ИИ-агент — исполнитель с ограниченными полномочиями.
Любое важное поведение должно быть подтверждено тестами и проверками CI.

---

## 0) Главный закон: работай только по Task Brief
ИИ-агент выполняет задачи **только** при наличии явного Task Brief (от пользователя/в задаче).

Task Brief обязан содержать:
- цель (Goal)
- границы (Scope / Non-scope)
- список файлов для чтения (Read-only)
- список файлов для изменения (Writable)
- политику Git / PR (Git / PR policy)
- критерии готовности (DoD)
- команды проверок (Commands)

Если Task Brief отсутствует или неполный — НЕ начинать работу.

### Режимы Task Brief

Task Brief может задавать один из двух режимов:

1. **Implementation mode** — стандартный режим работы с репозиторием. Агент обязан внести требуемые изменения в свою рабочую копию, но только в файлы из `Writable`.
2. **Proposal-only mode** — специальный режим для задач, где пользователь действительно не хочет менять working tree. `Writable` может быть `None`, а результатом является только текстовое предложение изменений.

Если Task Brief явно не указывает `Proposal-only`, использовать **Implementation mode**.

Запрет на commit / push / PR НЕ переводит задачу в proposal-only mode.
Обычный manual-review workflow выглядит так:

`implementation in Writable -> required checks -> leave working tree uncommitted -> final report -> stop`

То есть агенту разрешено и требуется изменить `Writable`-файлы в своей рабочей копии, чтобы пользователь мог просмотреть обычный file diff в интерфейсе.

`Writable: None` допустим только в явно обозначенном proposal-only режиме.

## 1) Разрешённые изменения (по умолчанию)
По умолчанию агент **может менять только то**, что указано в секции Writable Task Brief.

Любые изменения вне Writable запрещены.

Запрещено по умолчанию:
- рефакторинг “заодно”
- переезды директорий/переименования
- изменения инфраструктуры (docker/nginx/kafka)
- изменения контрактов
- изменения shared-кода
- изменения CI/Makefile/pre-commit

Если требуется — это должно быть явно разрешено в Task Brief.

---

## 2) Git / Commit / PR policy
По умолчанию ИИ-агент **НЕ имеет права**:

- создавать commits;
- делать amend существующих commits;
- выполнять `git push`;
- создавать или обновлять pull request;
- выполнять merge pull request.

Стандартная точка остановки агента:

`implementation -> required checks -> git diff / git status -> final report -> stop`

Commit, push, создание/обновление PR и merge разрешены только тогда, когда пользователь **явно разрешил соответствующее действие в текущем Task Brief**, если более приоритетные инструкции не требуют иного.

Важно: запрет commit / push / PR относится к Git-действиям, а не к редактированию working tree.

В **Implementation mode** агент не должен останавливать саму реализацию только из-за конфликта, относящегося исключительно к последующему commit / push / PR. Если изменение `Writable`-файлов и проверки разрешены, агент должен:

- выполнить изменения в `Writable`;
- выполнить доступные проверки;
- оставить изменения незакоммиченными, если commit не разрешён;
- остановиться перед запрещённым Git / PR действием;
- сообщить о конфликте только в части Git / PR.

Остановиться **до изменения файлов** следует только тогда, когда более приоритетная инструкция запрещает саму реализацию или изменение working tree, а не просто требует иной Git / PR workflow.

В **Proposal-only mode** агент не изменяет working tree и возвращает только требуемое текстовое предложение.

---

## 3) Protected core (НЕ трогать без явного разрешения)
По умолчанию агент НЕ имеет права изменять:

- `services/shared/**`
- `docs/contracts/**`
- `services/shared/schemas/**`
- `docs/policies/**`
- `docs/runbooks/**`
- `.github/**` (CI)
- `Makefile`, `pyproject.toml`, `pre-commit` конфигурации

Исключение: только если Task Brief явно разрешает изменения
и требует перечислить последствия/миграции/тесты.

---

## 4) Правила качества (без компромиссов)
Запрещено:
- ослаблять существующие тесты/ассерты ради “зелёного”
- удалять тесты без явного разрешения
- “чинить” flaky ретраями без устранения причины
- ловить широкий `Exception` вместо корректной обработки
- добавлять зависимости без явного разрешения

Если тест падает:
- исправь причину,
- либо измени тест ТОЛЬКО если контракт изменился (и это явно указано).

---

## 5) Тесты обязательны
Если изменение влияет на поведение:
- добавить/обновить тесты.

Если фиксится баг:
- сначала регрессионный тест, который падает,
- затем фикс,
- затем зелёный прогон.

---

## 6) Обязательные проверки перед сдачей
Перед финальным ответом агент обязан:
- выполнить команды из Task Brief (lint/type/tests/coverage и т.п.)
- или явно сказать, что выполнение невозможно в среде агента,
  и перечислить команды, которые должны быть запущены локально/в CI.

### Documentation impact review

Для каждой implementation-задачи обязателен следующий порядок:

`implementation -> verification -> documentation impact review -> documentation update if required -> task complete`

Implementation-задача не завершена, пока не выполнено одно из условий:

- затронутая документация обновлена;
- итоговый отчёт явно содержит `Documentation changes required: none`.

Definition of Done каждого будущего implementation Task Brief обязан включать:

- `Documentation impact reviewed: required.`
- `Affected documentation updated: required when applicable.`

При review необходимо рассмотреть по применимости `README.md`, архитектуру,
task history, API/contracts, runbooks, testing, roadmap, ADR и CI-документацию.
Известный drift нельзя откладывать на неопределённую будущую уборку.

## 7) Формат результата (обязательный отчёт)

### Implementation mode

Это стандартный режим.

Агент реально изменяет только `Writable`-файлы в своей рабочей копии. Изменения должны оставаться доступными пользователю для обычного file-diff review в интерфейсе.

В финальном сообщении агент обязан выдать:

1) Что сделано (коротко)
2) Список изменённых файлов
3) Какие тесты добавлены/изменены (сценарии), если применимо
4) Какие команды прогнаны и результат
5) Какие допущения сделаны
6) Что потенциально может сломаться (если применимо)
7) Статус Git / PR действий:
   - был ли создан commit;
   - выполнялся ли push;
   - создавался/обновлялся ли PR;
   - если нет — явно подтвердить, что working-tree changes оставлены пользователю на ручной review.

По умолчанию НЕ нужно дублировать весь `git diff` или полный содержимый изменённых файлов текстом в финальном ответе: пользователь просматривает изменения через обычный file diff интерфейса.
Печатать patch / unified diff в сообщении следует только если Task Brief явно этого требует.

### Proposal-only mode

Используется только если Task Brief прямо требует `Proposal-only`.

В этом режиме агент:

1) не изменяет working tree;
2) кратко описывает proposal;
3) показывает формат изменений, явно запрошенный Task Brief;
4) перечисляет проверки для ручного переноса;
5) подтверждает, что repository files не изменялись;
6) подтверждает статус commit / push / PR.
