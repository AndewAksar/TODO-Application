# AGENTS.md — Регламент работы ИИ-агента

Этот репозиторий развивается по принципам надёжной и безопасной разработки.
ИИ-агент — исполнитель с ограниченными полномочиями.
Любое важное поведение должно быть подтверждено тестами и проверками CI.

---

## 0) Главный закон: работай только по Task Brief
ИИ-агент выполняет задачи **только** при наличии явного Task Brief (от пользователя/в задаче).

Task Brief обязан содержать:
- цель (Goal)
- границы (Scope / Non-scope)
- список файлов для чтения (Read-only)
- список файлов для изменения (Writable)
- политику Git / PR (Git / PR policy)
- критерии готовности (DoD)
- команды проверок (Commands)

Если Task Brief отсутствует или неполный — НЕ начинать работу.

### Режимы Task Brief

Task Brief может задавать один из двух режимов:

1. **Implementation mode** — агент имеет право изменять только файлы из `Writable`.
2. **Proposal-only mode** — репозиторий остаётся неизменным; `Writable` может быть `None`, а результатом работы является текстовое предложение изменений, обычно в формате unified diff.

`Writable: None` в proposal-only задаче НЕ означает, что агенту «нечего делать».
Анализ репозитория и генерация предлагаемого diff/patch не являются изменением файлов репозитория.

---

## 1) Разрешённые изменения (по умолчанию)
По умолчанию агент **может менять только то**, что указано в секции Writable Task Brief.

Любые изменения вне Writable запрещены.

Запрещено по умолчанию:
- рефакторинг “заодно”
- переезды директорий/переименования
- изменения инфраструктуры (docker/nginx/kafka)
- изменения контрактов
- изменения shared-кода
- изменения CI/Makefile/pre-commit

Если требуется — это должно быть явно разрешено в Task Brief.

---

## 2) Git / Commit / PR policy
По умолчанию ИИ-агент **НЕ имеет права**:

- создавать commits;
- делать amend существующих commits;
- выполнять `git push`;
- создавать или обновлять pull request;
- выполнять merge pull request.

Стандартная точка остановки агента:

`implementation -> required checks -> git diff / git status -> final report -> stop`

Commit, push, создание/обновление PR и merge разрешены только тогда, когда пользователь **явно разрешил соответствующее действие в текущем Task Brief**, если более приоритетные инструкции не требуют иного.

Конфликт, относящийся только к Git / commit / push / PR, не должен сам по себе блокировать безопасную read-only работу.
Если Task Brief работает в **proposal-only mode**, агент должен, насколько это разрешено более приоритетными инструкциями:

- прочитать и проанализировать разрешённые файлы;
- подготовить требуемый proposal / unified diff;
- не скрывать proposal только из-за того, что Git-действия запрещены Task Brief;
- отдельно сообщить о любом оставшемся конфликте Git / PR policy.

Если более приоритетная инструкция действительно делает сам proposal-only режим невозможным, агент должен явно сообщить, что конфликт вызван средой выполнения, а не содержанием репозитория.

---

## 3) Protected core (НЕ трогать без явного разрешения)
По умолчанию агент НЕ имеет права изменять:

- `services/shared/**`
- `docs/contracts/**`
- `services/shared/schemas/**`
- `docs/policies/**`
- `docs/runbooks/**`
- `.github/**` (CI)
- `Makefile`, `pyproject.toml`, `pre-commit` конфигурации

Исключение: только если Task Brief явно разрешает изменения
и требует перечислить последствия/миграции/тесты.

---

## 4) Правила качества (без компромиссов)
Запрещено:
- ослаблять существующие тесты/ассерты ради “зелёного”
- удалять тесты без явного разрешения
- “чинить” flaky ретраями без устранения причины
- ловить широкий `Exception` вместо корректной обработки
- добавлять зависимости без явного разрешения

Если тест падает:
- исправь причину,
- либо измени тест ТОЛЬКО если контракт изменился (и это явно указано).

---

## 5) Тесты обязательны
Если изменение влияет на поведение:
- добавить/обновить тесты.

Если фиксится баг:
- сначала регрессионный тест, который падает,
- затем фикс,
- затем зелёный прогон.

---

## 6) Обязательные проверки перед сдачей
Перед финальным ответом агент обязан:
- выполнить команды из Task Brief (lint/type/tests/coverage и т.п.)
- или явно сказать, что выполнение невозможно в среде агента,
  и перечислить команды, которые должны быть запущены локально/в CI.

---

## 7) Формат результата (обязательный отчёт)

### Proposal-only mode

Если Task Brief требует только предложение изменений и запрещает модификацию репозитория, агент обязан:

1) кратко описать предлагаемое изменение;
2) перечислить файлы, которых касается proposal;
3) показать **unified diff** для каждого предлагаемого изменения:
   - с путями файлов;
   - с контекстом;
   - с удаляемыми строками `-`;
   - с добавляемыми строками `+`;
   - с `@@`-hunks;
4) перечислить проверки, которые пользователь должен выполнить после ручного переноса;
5) явно подтвердить, что файлы репозитория агентом не изменялись;
6) явно подтвердить статус commit / push / PR.

Если Task Brief явно не требует иного, normal final-code blocks НЕ заменяют unified diff в proposal-only mode.

### Implementation mode

Если агент реально изменял файлы, в финальном сообщении он обязан выдать:

1) Что сделано (коротко)
2) Список изменённых файлов
3) Какие тесты добавлены/изменены (сценарии)
4) Какие команды прогнаны и результат
5) Какие допущения сделаны
6) Что потенциально может сломаться (если применимо)
7) `git diff` по изменённым Writable-файлам либо эквивалентный patch, если Task Brief явно не требует другой формат
8) Статус Git / PR действий:
   - был ли создан commit;
   - выполнялся ли push;
   - создавался/обновлялся ли PR;
   - если нет — явно подтвердить, что изменения оставлены пользователю на ручной review.

## 8) Если задача “на тестирование”
Правила дополнительно:
- unit-тесты не используют сеть/БД/брокер
- integration/contract тесты — только если явно требуется
- flaky недопустимы, quarantined допускается только по Task Brief
