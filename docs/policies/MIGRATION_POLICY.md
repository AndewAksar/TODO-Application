# MIGRATION_POLICY

## 1. Назначение

Эта политика фиксирует **обязательные правила управления схемой базы данных и системой миграций**.

Миграции рассматриваются как:

- часть исходного кода;
- механизм эволюции схемы БД;
- архитектурный инвариант согласованности между кодом и базой данных.

**Цель политики:**

- обеспечить воспроизводимую эволюцию схемы БД;
- исключить рассинхронизацию между кодом и базой данных;
- предотвратить потерю migration-файлов;
- зафиксировать canonical workflow генерации и применения миграций;
- обеспечить проверяемость миграций через CI.

---

## 2. Область применения

Политика применяется ко всем операциям, связанным со схемой БД:

- создание новых миграций;
- применение миграций;
- откат миграций;
- изменение SQLAlchemy моделей;
- проверка схемы в CI.

Политика распространяется на:

- Alembic configuration;
- migration scripts;
- Makefile команды;
- Docker tooling workflow;
- CI/CD pipeline.

Исключения допускаются **только**:

- документированно (ADR / waiver);
- временно;
- с явным сроком пересмотра.

---

## 3. Migration Boundary

**Migration boundary** — это слой, отвечающий за согласованность между кодом и схемой БД.

Migration boundary включает:

- Alembic configuration (`alembic.ini`);
- каталог `migrations`;
- каталог `migrations/versions`;
- Makefile команды миграций;
- Docker tooling workflow.

Любое изменение схемы БД **обязано проходить через migration boundary**.

---

## 4. Архитектурная модель миграций

Система миграций разделяет **две категории операций**.

---

### 4.1 Migration Generation

Создание новой миграции:
```aiignore
alembic revision -m "message"
```
Это операция **генерации исходного кода**.

Результатом операции является новый migration script в каталоге:|
```aiignore
migrations/versions
```
Требования:

- файл должен появиться в working tree;
- файл должен быть виден в `git status`;
- файл должен быть проверен разработчиком.

---

### 4.2 Migration Execution

Применение миграций:
```aiignore
alembic upgrade head
```
Это **операционная операция**.

Она может выполняться:

- в runtime container;
- в tooling container;
- в CI pipeline;
- в deployment pipeline.

---

## 5. Migration Invariants

Следующие инварианты являются обязательными.

---

### 5.1 Миграции являются частью исходного кода

Каждая миграция обязана:

- находиться в репозитории;
- иметь файл в `migrations/versions`;
- попадать в `git status`;
- проходить code review.

Миграция считается созданной **только если файл появился в working tree**.

---

### 5.2 Schema changes запрещены без миграции

Запрещено:

- изменять структуру таблиц вручную в БД;
- изменять SQLAlchemy модели без создания миграции;
- применять schema changes напрямую через SQL.

Любое изменение моделей, влияющее на схему БД, обязано сопровождаться migration script.

---

### 5.3 Генерация миграций должна происходить в tooling container

Canonical workflow генерации миграций:

- выполняется через **tooling container**;
- использует **bind mount проекта**;
- создаёт файл миграции непосредственно в working tree.

Недопустимо:

- создавать миграции внутри ephemeral container;
- генерировать migration files, которые остаются только внутри контейнера.

---

## 6. Docker Workflow

Контейнерная архитектура разделяет роли среды выполнения.

---

### 6.1 Runtime container

`api`

Назначение:

- запуск приложения;
- применение миграций (`upgrade head`).

Runtime container **не является canonical средой генерации миграций**.

---

### 6.2 Tooling container

`api-tooling`

Назначение:

- pytest;
- ruff;
- mypy;
- служебные команды разработки;
- генерация миграций.

Tooling container должен:

- иметь Alembic;
- иметь доступ к проекту через bind mount.

---

## 7. Canonical Workflow

Canonical workflow генерации миграций:
```aiignore
make makemigration M="migration message"
```

Команда должна:

- запускать tooling container;
- генерировать migration script;
- создавать файл в working tree.

После генерации разработчик обязан:

1. проверить содержимое миграции;
2. убедиться в отсутствии лишних изменений;
3. добавить файл в git.

---

## 8. Требования к migration scripts

Каждый migration script обязан:

- иметь осмысленное имя;
- быть атомарным по смыслу;
- не содержать случайных изменений;
- быть проверяемым на чистой базе.

Autogenerated код должен быть **проверен вручную**.

---

## 9. CI-проверка миграций

CI pipeline обязан проверять корректность миграций.

Минимальная проверка:
```aiignore
alembic upgrade head
```
на чистой базе.

Цель проверки:

- убедиться, что все миграции применяются корректно;
- убедиться, что схема БД соответствует текущему коду.

CI обязан падать, если:

- миграции не применяются;
- обнаружена несовместимость схемы.

---

## 10. Запрещённые практики

Запрещено:

- генерировать миграции внутри ephemeral container без bind mount;
- считать миграцию созданной, если файла нет в репозитории;
- применять schema changes вручную;
- удалять migration files из истории без ADR.

---

## 11. Definition of Done (Migrations)

Изменение схемы БД считается завершённым, если:

- создан migration script;
- файл находится в `migrations/versions`;
- файл появился в `git status`;
- миграция успешно применяется;
- CI pipeline зелёный.
