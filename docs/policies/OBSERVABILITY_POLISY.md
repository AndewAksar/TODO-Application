# Observability Policy

## Purpose

Эта политика фиксирует обязательные требования к наблюдаемости системы.

Observability рассматривается как:
- эксплуатационное свойство системы,
- архитектурный инвариант,
- обязательное условие диагностики инцидентов.

Цель — обеспечить возможность понять состояние системы
по внешним сигналам без изменения кода.

---

## Logging

Обязательные требования:

- Используется структурированное логирование.
- Уровни логов: DEBUG, INFO, WARNING, ERROR.
- Логи пишутся в stdout (контейнерная среда).
- Исключения логируются централизованно.

Запрещено логировать:
- JWT-токены (полностью или частично),
- пароли,
- секреты,
- private keys,
- sensitive headers.

Любая ошибка, приводящая к HTTP 5xx,
обязана быть зафиксирована в логах.

---

## Healthchecks

Каждый сервис обязан иметь health endpoint:

- `/health` — базовая доступность сервиса.

Health endpoint:
- не зависит от внешних клиентов,
- используется для readiness/liveness,
- проверяется в CI (docker smoke tests).

Отсутствие health endpoint считается нарушением политики.

---

## Error Handling

Требования:

- Запрещено silent failure (подавление исключений).
- Все необработанные исключения:
  - логируются,
  - возвращают корректный HTTP-статус.
- Бизнес-ошибки и системные ошибки различаются явно.

---

## Docker & Runtime Signals

Обязательные сигналы:

- health status контейнеров,
- restart policy,
- доступность основных HTTP endpoints.

Runtime-состояние системы проверяется
в CI через docker smoke pipeline.

---

## Incident Diagnostics

При инцидентах используются:
- логи сервисов,
- health endpoints,
- docker compose status.

Подробные инструкции по диагностике
фиксируются в соответствующих runbooks.

---

- конкретные инструменты мониторинга,
- реализацию логирования в коде,
- пошаговые сценарии устранения инцидентов.
