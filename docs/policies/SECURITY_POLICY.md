# SECURITY_POLICY

## 1. Назначение

Эта политика фиксирует **обязательные требования к безопасности приложения** как к системе **инвариантов**.

Безопасность рассматривается как:

- архитектурное свойство;
- набор обязательных границ;
- механизм ограничения поведения кода и ИИ-агентов.

**Цель политики:**

- определить security boundary системы;
- зафиксировать обязательные правила работы с секретами, токенами и паролями;
- минимизировать риск утечек;
- исключить «самодеятельность» в вопросах безопасности.

---

## 2. Область применения

Политика применяется ко **всем сервисам репозитория** и ко **всем уровням системы**:

- HTTP API;
- доступ к БД;
- JWT и аутентификация;
- обработка паролей;
- конфигурация и секреты;
- логирование и observability.

Исключения допускаются **только**:

- документированно (ADR / waiver);
- временно;
- с явным сроком пересмотра.

---

## 3. Security Boundary

**Security boundary** в текущей архитектуре включает:

- `get_current_user`;
- JWT decode;
- проверку пароля;
- DB-layer как источник истины пользователя.

Любой код, проходящий через security boundary, **обязан**:

- не раскрывать лишнюю информацию;
- быть детерминированным;
- иметь тестовое подтверждение
  (см. `docs/policies/TESTING_POLICY.md`).

---

## 4. Работа с секретами

### 4.1 Обязательные правила

- Секреты **запрещено** хранить в коде.
- Секреты загружаются **только** через environment variables.
- Отсутствие обязательного секрета должно приводить к:
  - fail-fast при старте, **или**
  - явной ошибке при первом использовании.
- Логирование секретов **запрещено**.

### 4.2 Запрещено

- использовать дефолтные ключи (`"secret"`, `"123"`, `"dev"` и т. п.);
- коммитить `.env` с реальными значениями;
- передавать секреты через query-параметры или body.

---

## 5. JWT-инварианты

### 5.1 Обязательные требования

JWT **обязан** содержать следующие claims:

- `sub`;
- `iat`;
- `exp`.

Требования:

- `sub` — строковое представление `user_id` (`int`);
- `exp` — **обязателен**;
- алгоритм подписи задаётся конфигурацией.

### 5.2 Обработка ошибок

Любая ошибка:
- отсутствие токена;
- неправильный формат;
- просроченный токен;
- пользователь не найден;
- обязана приводить к единому ответу: `401 Unauthorized`.

Исключение: инфраструктурные ошибки.
- Инфраструктурные ошибки (например, недоступность БД, ошибки соединения, таймауты пула) не относятся к ошибкам аутентификации.
- В таких случаях сервис обязан возвращать:
  - `503 Service Unavailable` (без раскрытия деталей наружу);
  - и фиксировать причину в логах/метриках.

**Запрещено:**
- раскрывать детали причины;
- различать “пользователь не найден” и “битый токен”.

## 6) Работа с паролями
### 6.1 Обязательные правила
- Пароли хранятся только в виде хеша.
- Используется проверенный алгоритм (bcrypt).
- Соль генерируется автоматически.
- Сравнение выполняется только через verify-функцию.

### 6.2 Запрещено
- хранить пароль в открытом виде;
- логировать пароль;
- реализовывать собственную криптографию.

## 7) Ошибки и сообщения
Сообщения об ошибках не должны раскрывать:
- внутреннюю структуру БД;
- наличие/отсутствие пользователя;
- детали валидации токена.
- В продакшене stacktrace не возвращается клиенту.
- Внешний ответ на инфраструктурные ошибки не раскрывает деталей, но код ответа обязан отличать outage от auth-failure.

## 8) Логирование
Разрешено:
- логировать факт неуспешной аутентификации.

Запрещено:
- логировать токены;
- логировать хеши;
- логировать секреты;
- логировать Authorization header полностью.

## 9) Требование тестового подтверждения
Любое изменение в:
- JWT;
- password handling;
- security boundary;
- кодах ошибок;

обязано сопровождаться тестами (см. TESTING_POLICY).

## 10) Definition of Done (Security)
Изменение, затрагивающее безопасность, считается завершённым, если:
- соблюдены все правила политики;
- добавлены/обновлены тесты;
- проверено отсутствие утечек в логах;
- CI зелёный.
