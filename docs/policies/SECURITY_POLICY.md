# SECURITY_POLICY

## 1. Назначение

Эта политика фиксирует **обязательные требования к безопасности приложения** как к системе **инвариантов**.

Безопасность рассматривается как:

- архитектурное свойство;
- набор обязательных границ;
- механизм ограничения поведения кода и ИИ-агентов.

**Цель политики:**

- определить security boundary системы;
- зафиксировать обязательные правила работы с секретами, токенами и паролями;
- минимизировать риск утечек;
- исключить «самодеятельность» в вопросах безопасности.

---

## 2. Область применения

Политика применяется ко **всем сервисам репозитория** и ко **всем уровням системы**:

- HTTP API;
- доступ к БД;
- JWT и аутентификация;
- обработка паролей;
- конфигурация и секреты;
- логирование и observability.

Исключения допускаются **только**:

- документированно (ADR / waiver);
- временно;
- с явным сроком пересмотра.

---

## 3. Security Boundary

**Security boundary** в текущей архитектуре включает:

- `get_current_user`;
- JWT decode;
- проверку пароля;
- DB-layer как источник истины пользователя.

Любой код, проходящий через security boundary, **обязан**:

- не раскрывать лишнюю информацию;
- быть детерминированным;
- иметь тестовое подтверждение
  (см. `docs/policies/TESTING_POLICY.md`).

---

## 4. Работа с секретами

### 4.1 Обязательные правила

- Секреты **запрещено** хранить в коде.
- Секреты загружаются **только** через environment variables.
- Отсутствие обязательного секрета должно приводить к:
  - fail-fast при старте, **или**
  - явной ошибке при первом использовании.
- Логирование секретов **запрещено**.

### 4.2 Запрещено

- использовать дефолтные ключи (`"secret"`, `"123"`, `"dev"` и т. п.);
- коммитить `.env` с реальными значениями;
- передавать секреты через query-параметры или body.

---

## 5. JWT-инварианты

### 5.1 Обязательные требования

JWT **обязан** содержать следующие claims:

- `sub`;
- `iat`;
- `exp`.

Требования:

- `sub` — строковое представление `user_id` (`int`);
- `exp` — **обязателен**;
- алгоритм подписи задаётся конфигурацией.
