# ADR-000X: Separation of Runtime Image and Tooling Workspace

## Status
Accepted

## Context

Проект использует Docker Compose для локальной разработки
и CI/CD для автоматических проверок.

В процессе развития проекта возникли разные категории операций:

1. Runtime операции:
   - запуск API сервиса
   - обработка запросов
   - взаимодействие с Kafka и БД

2. Инженерные операции:
   - запуск тестов
   - статический анализ (ruff, mypy)
   - форматирование
   - запуск Alembic миграций
   - диагностика схемы БД

Изначально все инструменты могли быть установлены
в runtime-контейнере сервиса API.

Однако это приводит к ряду проблем:

- runtime-образ содержит dev/test зависимости
- увеличивается размер образа
- увеличивается поверхность ошибок
- runtime среда смешивается с инженерными инструментами
- CI/CD становится менее прозрачным

Требуется явное разделение среды исполнения приложения
и среды инженерных операций.

## Decision

Принята архитектура разделения контейнеров:

### Runtime Container

Контейнер `api` содержит только runtime зависимости
и используется исключительно для запуска приложения.

Содержит:

- FastAPI
- SQLAlchemy
- runtime зависимости
- uvicorn
- код сервисов

Не содержит:

- pytest
- ruff
- mypy
- Alembic
- dev/test зависимости

Назначение:

- запуск API
- обработка HTTP запросов
- взаимодействие с инфраструктурой

---

### Tooling Container

Контейнер `api-tooling` используется как инженерная рабочая среда.

Содержит:

- runtime зависимости
- dev зависимости
- test зависимости
- pytest
- ruff
- mypy
- Alembic

Назначение:

- запуск тестов
- запуск линтеров
- запуск typecheck
- выполнение Alembic миграций
- диагностика схемы БД

Контейнер используется как ephemeral workspace:
```
docker compose --profile test run --rm api-tooling <command>
```
---

### Разделение операций

Runtime контейнер:

- запуск сервиса
- runtime выполнение приложения

Tooling контейнер:

- lint
- format
- typecheck
- pytest
- Alembic upgrade
- Alembic history
- Alembic heads
- Alembic current

Таким образом runtime контейнер не содержит
инженерных инструментов.

---

### Docker Image Strategy

Используется multi-stage Dockerfile:

- base — общая база
- runtime — минимальный образ для API
- tooling — образ с dev/test инструментами

Это позволяет:

- минимизировать runtime image
- ускорить CI/CD
- уменьшить attack surface

---

## Alternatives Considered

### 1. Один контейнер для всего

Отклонено.

Минусы:

- runtime содержит dev/test инструменты
- увеличенный размер образа
- смешивание ответственности среды
- сложнее поддерживать CI/CD

---

### 2. Отдельный контейнер только для тестов

Отклонено.

Минусы:

- дублирование логики tooling
- Alembic и диагностика БД всё равно требуют отдельной среды
- усложнение инфраструктуры

---

### 3. Выполнение tooling операций на хосте

Отклонено.

Минусы:

- зависимость от локального окружения разработчика
- несовпадение с CI средой
- потеря воспроизводимости

---

## Consequences

### Плюсы

- минимальный runtime образ
- четкое разделение ответственности контейнеров
- воспроизводимая среда разработки
- более безопасный runtime контейнер
- удобная интеграция с CI/CD
- единый workspace для инженерных операций

### Минусы

- дополнительный контейнер
- необходимость поддерживать tooling-образ
- немного более сложный Dockerfile

Однако эти накладные расходы оправданы
архитектурной чистотой и воспроизводимостью среды.
