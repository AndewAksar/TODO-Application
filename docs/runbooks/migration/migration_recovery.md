# Migration Recovery Runbook

## 1. Назначение

Этот runbook описывает **процедуры восстановления системы миграций** в случае ошибок или повреждения миграционной цепочки.

Документ используется когда:

- миграция применена некорректно
- база находится на неправильной ревизии
- потерян migration file
- нарушена цепочка миграций
- база данных и код рассинхронизированы

Runbook реализует правила:

docs/policies/MIGRATION_POLICY.md

---

# 2. Базовая диагностика

Перед восстановлением необходимо определить состояние системы.

### Проверка текущей ревизии базы

```
alembic current
```

---

### Проверка последних ревизий

```
alembic heads
```

---

### Проверка полной истории

```
alembic history
```

---

### Проверка состояния схемы

Попробовать применить миграции:

```
alembic upgrade head
```

Если команда завершается ошибкой — требуется восстановление.

---

# 3. Сценарии восстановления

---

## 3.1 База находится на неправильной ревизии

Симптом:

```
alembic current
```

показывает ревизию, отличную от ожидаемой.

Решение:

Привести базу к нужной ревизии.

```
alembic upgrade head
```

или

```
alembic downgrade <revision>
```

---

## 3.2 Ошибка в последней миграции

Симптом:

```
alembic upgrade head
```

падает на последней миграции.

Решение:

1. откатить последнюю миграцию

```
alembic downgrade -1
```

2. исправить migration script

3. повторно применить миграцию

```
alembic upgrade head
```

---

## 3.3 Потерян migration file

Симптом:

- база находится на ревизии
- файл миграции отсутствует в репозитории

Проверка:

```
alembic current
```

Если ревизия отсутствует в `migrations/versions`, цепочка нарушена.

Решение:

1. восстановить файл миграции из git history
2. либо пересоздать миграцию
3. убедиться, что цепочка ревизий восстановлена

---

## 3.4 Несколько head

Симптом:

```
alembic heads
```

возвращает несколько ревизий.

Решение:

создать merge migration.

```
alembic merge -m "merge heads" <rev1> <rev2>
```

---

## 3.5 Миграция была создана внутри контейнера

Симптом:

- команда `alembic revision` выполнялась
- файла нет в репозитории

Причина:

миграция была создана внутри ephemeral container.

Решение:

1. пересоздать миграцию через canonical workflow
2. убедиться, что файл появился в working tree

---

# 4. Полное восстановление схемы

Если состояние БД сильно повреждено, можно восстановить её полностью.

Процедура:

1. удалить базу данных
2. создать новую базу
3. применить все миграции

```
alembic upgrade head
```

Этот процесс восстанавливает схему с нуля.

---

# 5. Проверка после восстановления

После восстановления необходимо проверить:

1. текущую ревизию

```
alembic current
```

2. запуск приложения

3. выполнение основных запросов

4. прохождение CI pipeline

---

# 6. Definition of Done

Восстановление считается завершённым, если:

- база находится на ревизии `head`
- цепочка миграций восстановлена
- приложение запускается корректно
- CI pipeline проходит успешно

---

# 7. Расширенное объяснение (для разработчиков)

Этот раздел объясняет **почему происходят проблемы с миграциями** и как их предотвращать.

---

## 7.1 Миграции — это журнал изменений схемы

Alembic работает как **журнал изменений схемы базы данных**.

Каждая миграция:

- имеет уникальный revision id
- знает свою предыдущую ревизию
- формирует цепочку изменений

Пример цепочки:

```
base -> a1b2c3 -> d4e5f6 -> g7h8i9
```

Каждая миграция зависит от предыдущей.

Если одна из них потеряна — цепочка разрывается.

---

## 7.2 Почему возникают несколько head

Это происходит когда:

- два разработчика создают миграции параллельно
- ветки объединяются

Пример:

```
base
  ├─ a1b2c3
  │    └─ d4e5f6
  └─ x7y8z9
```

В этом случае Alembic видит два head.

Merge migration объединяет ветки.

---

## 7.3 Почему опасны потерянные миграции

Если migration file исчезает:

- база содержит изменения
- код не знает об этих изменениях

В результате:

- цепочка ревизий ломается
- невозможно выполнить upgrade
- невозможно выполнить downgrade

Поэтому MIGRATION_POLICY требует:

- хранить миграции в git
- не удалять их без ADR

---

## 7.4 Почему важна проверка на чистой базе

Иногда миграции работают только на уже существующей базе.

Но новая установка должна уметь:

```
alembic upgrade head
```

с нуля.

CI проверяет именно этот сценарий.

---

## 7.5 Почему опасны ephemeral контейнеры

Docker может создавать временные контейнеры.

Если migration file создаётся внутри такого контейнера:

- файл существует только внутри контейнера
- после удаления контейнера он исчезает

Поэтому canonical workflow требует:

- использовать bind mount проекта
- создавать файлы в working tree

---

## 7.6 Когда допустимо полное восстановление базы

Полное пересоздание базы допустимо только:

- в development
- в CI

В production обычно используется только:

```
alembic upgrade
```

Полное удаление базы требует отдельной процедуры восстановления данных.
