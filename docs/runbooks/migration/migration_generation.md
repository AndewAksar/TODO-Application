# Migration Generation Runbook

## 1. Назначение

Этот runbook описывает **canonical workflow создания новых миграций базы данных**.

Документ применяется при:

- изменении SQLAlchemy моделей;
- добавлении новых таблиц;
- изменении колонок;
- добавлении индексов;
- изменении ограничений.

Runbook реализует правила, определённые в:

```
docs/policies/MIGRATION_POLICY.md
```

---

# 2. Основной принцип

Миграции являются **частью исходного кода**.

Каждая миграция обязана:

- находиться в каталоге `migrations/versions`
- появляться в `git status`
- проходить code review
- успешно применяться на чистой базе

Миграция считается созданной **только если файл появился в working tree**.

---

# 3. Canonical workflow

Создание миграции выполняется через Makefile.

```
make makemigration M="migration message"
```

Пример:

```
make makemigration M="add users table"
```

Команда выполняет:

- запуск tooling container
- выполнение Alembic revision
- создание migration script

---

# 4. Где должен появиться migration file

После выполнения команды новый файл должен появиться в каталоге:

```
migrations/versions
```

Пример:

```
migrations/versions/1c9c115cdf19_add_users_table.py
```

Проверка:

```
git status
```

Ожидаемый результат:

```
new file: migrations/versions/<revision>_<message>.py
```

Если файл не появился в working tree — **workflow нарушен**.

---

# 5. Проверка содержимого миграции

Autogenerated код **обязан быть проверен вручную**.

Перед коммитом необходимо проверить:

### 5.1 Проверить операции upgrade

```
def upgrade():
```

Проверить:

- создаётся ли нужная таблица
- добавлены ли нужные колонки
- нет ли лишних изменений

---

### 5.2 Проверить операции downgrade

```
def downgrade():
```

Каждая операция upgrade должна иметь обратную операцию.

---

### 5.3 Проверить случайные изменения

Autogenerate иногда добавляет лишние операции.

Проверить отсутствие:

- случайных индексов
- лишних alter table
- изменений unrelated таблиц

---

# 6. Проверка миграции

После генерации миграции необходимо убедиться, что она применима.

Выполнить:

```
make migrate
```

Команда выполняет:

```
alembic upgrade head
```

Если миграция применена успешно — схема БД синхронизирована.

---

# 7. Проверка на чистой базе

Рекомендуется проверить миграцию на пустой базе.

Процедура:

1. удалить существующую БД
2. создать новую
3. выполнить

```
alembic upgrade head
```

Это подтверждает, что **вся цепочка миграций корректна**.

---

# 8. Коммит миграции

После проверки необходимо добавить файл в git.

```
git add migrations/versions/<file>.py
```

Затем выполнить коммит.

Пример:

```
git commit -m "db(migration): add users table"
```

---

# 9. Типовые ошибки

## 9.1 Migration file не появился

Причина:

- миграция была создана внутри ephemeral container
- отсутствует bind mount проекта

Решение:

- использовать canonical workflow
- убедиться, что файл появился в working tree

---

## 9.2 Autogenerate создал лишние изменения

Причина:

- несинхронизированные модели
- изменения вне ORM

Решение:

- вручную отредактировать migration script

---

## 9.3 Ошибка применения миграции

Причина может быть:

- несовместимость типов
- неправильный downgrade
- конфликт индексов

Решение:

- исправить migration script
- повторно применить миграцию

---

# 10. Definition of Done

Создание миграции считается завершённым, если:

- migration script создан
- файл появился в `migrations/versions`
- файл присутствует в `git status`
- миграция успешно применяется
- CI pipeline проходит успешно
