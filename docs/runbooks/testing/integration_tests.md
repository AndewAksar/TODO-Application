# INTEGRATION TEST PLAYBOOK

## Назначение
Этот документ описывает порядок написания и запуска интеграционных тестов.

Интеграционный тест проверяет взаимодействие компонентов:
- приложение ↔ база данных
- приложение ↔ брокер сообщений
- приложение ↔ файловая система
- приложение ↔ внешний сервис (через адаптер)

Цель — подтвердить, что контракты и интеграции работают в реальной среде.

---

## 1. Когда обязателен интеграционный тест

Интеграционный тест обязателен, если:

- добавляется или меняется взаимодействие с БД;
- добавляется публикация/чтение события;
- меняется схема данных;
- меняется конфигурация инфраструктуры;
- обнаружен дефект на уровне взаимодействия компонентов.

Если поведение зависит от инфраструктуры — unit-теста недостаточно.

---

## 2. Границы интеграционного теста

Интеграционный тест:

- использует реальные зависимости (Postgres, Kafka и т.д.);
- запускается в изолированной среде (docker compose);
- не использует моки вместо инфраструктуры;
- проверяет наблюдаемое поведение, а не внутренности.

Это НЕ e2e:
- не проверяет весь продукт целиком;
- не проходит через UI;
- не тестирует фронтенд.

---

## 3. Подготовка окружения

### Шаг 1 — Изолированная среда

Тест должен запускаться:

- в отдельной БД/схеме;
- без зависимости от локальных данных;
- без необходимости ручной подготовки.

Использовать:
- docker compose;
- переменные окружения;
- автоматический bootstrap (миграции).

---

### Шаг 2 — Контроль состояния

Перед тестом:

- база должна быть в чистом состоянии;
- миграции применены;
- брокер поднят и готов;
- нет данных от предыдущих запусков.

После теста:

- состояние не должно влиять на следующий тест;
- использовать транзакции, rollback или очистку.
