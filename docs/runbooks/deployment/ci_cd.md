# CI/CD Runbook

## Назначение

Этот документ описывает процесс проверки, сборки, публикации и развёртывания TODO Application с использованием GitHub Actions, GHCR, Docker Compose и deployment-скрипта.

Документ предназначен для разработчика или оператора, которому необходимо:

- понять полный путь изменений от Pull Request до production;
- проверить состояние CI;
- найти опубликованный Docker-образ;
- выполнить пробное развёртывание;
- выполнить production-развёртывание;
- диагностировать типовые ошибки CI/CD.

## Общая схема

Полный процесс состоит из следующих этапов:

1. Разработчик отправляет изменения в рабочую ветку и открывает Pull Request.
2. GitHub Actions запускает проверки кода, тесты, проверку миграций и Docker smoke test.
3. После объединения изменений с `main` GitHub Actions собирает API-образ.
4. Готовый образ публикуется в GitHub Container Registry с тегом полного SHA коммита.
5. Workflow `Deploy rehearsal` проверяет production-развёртывание на временном GitHub runner.
6. Workflow `Deploy production` передаёт конфигурацию на VDS и запускает выбранный образ.
7. После развёртывания выполняется проверка публичного health endpoint.

## Continuous Integration

Основной CI workflow расположен в `.github/workflows/ci.yml`.

Он автоматически запускается:

- для каждого Pull Request;
- после отправки изменений в ветку `main`.

Для одной ветки одновременно выполняется только последний запуск workflow. Если в ту же ветку отправлен новый коммит, предыдущий незавершённый запуск отменяется.

### Job `checks`

Проверяет исходный код без запуска инфраструктуры приложения:

1. Устанавливает Python 3.12 и пакетный менеджер `uv`.
2. Устанавливает зависимости строго по `uv.lock`.
3. Выполняет линтинг через `ruff check`.
4. Проверяет форматирование через `ruff format --check`.
5. Выполняет статическую проверку типов через `mypy`.
6. Запускает pytest-тесты, кроме интеграционных и помеченных как `flaky`.

Ошибка любого шага завершает job и блокирует публикацию образа.

### Job `integration`

Проверяет взаимодействие API с настоящим PostgreSQL:

1. Создаёт изолированный Compose-проект `ci-integration`.
2. Очищает возможные контейнеры и тома от предыдущего запуска.
3. Выполняет `make test-integration`.
4. После проверки выводит состояние контейнеров.
5. При ошибке выводит последние логи.
6. Всегда удаляет созданные контейнеры, сети и тома.

Интеграционные тесты выполняются через tooling-контейнер, а не через локальное Python-окружение GitHub runner.

### Job `migration-check`

Проверяет, что Alembic может создать актуальную схему базы данных с нуля:

1. Создаёт изолированный Compose-проект `ci-migration-check`.
2. Удаляет старые контейнеры и тома.
3. Запускает PostgreSQL на чистом томе.
4. Ожидает перехода PostgreSQL в состояние `healthy`.
5. Выполняет `alembic upgrade head` через контейнер `api-tooling`.
6. При ошибке выводит состояние контейнеров и логи.
7. Всегда удаляет временную инфраструктуру.

Эта проверка обнаруживает повреждённую или неполную последовательность миграций до развёртывания приложения.

### Job `docker-smoke`

Проверяет сборку и совместный запуск локального Docker Compose-контура:

1. Проверяет синтаксис Compose-конфигурации.
2. Собирает Docker-образы.
3. Запускает сервисы в фоновом режиме.
4. Ожидает готовности PostgreSQL, ZooKeeper, Kafka и API.
5. Проверяет API через `http://localhost:8008/health`.
6. Проверяет доступность Nginx через `http://localhost:8080/`.
7. Проверяет, что защищённый endpoint `/auth/me` без токена возвращает `401 Unauthorized`.
8. При ошибке выводит состояние и логи контейнеров.
9. Всегда удаляет временную инфраструктуру.

Этот job проверяет полный локальный контур разработки. Он отличается от production-контура, в который Kafka, ZooKeeper, scheduler и mailer пока не входят.

### Job `publish-image`

Публикация API-образа выполняется только после `push` в `main` и только при успешном завершении:

- `checks`;
- `integration`;
- `migration-check`;
- `docker-smoke`.

Workflow собирает `runtime`-этап из `services/api_gateway/Dockerfile` и публикует образ:

```text
ghcr.io/andewaksar/todo-application-api:<full-commit-sha>
```

В качестве тега используется полный SHA Git-коммита. Благодаря этому каждая версия образа однозначно связана с исходным кодом, а при развёртывании можно выбрать конкретную проверенную версию.

Публикация выполняется с помощью встроенного `GITHUB_TOKEN`. Job получает право `packages: write`, тогда как остальные части workflow работают только с правом чтения репозитория.

## Пробное развёртывание

Workflow пробного развёртывания расположен в `.github/workflows/deploy-rehearsal.yml`.

Он запускается вручную через GitHub Actions и принимает параметр `image_tag` — тег ранее опубликованного API-образа в GHCR. Для воспроизводимой проверки следует указывать полный SHA Git-коммита.

Пробное развёртывание выполняется не на production-сервере, а на временном GitHub runner с Ubuntu.

### Последовательность выполнения

Workflow выполняет следующие действия:

1. Загружает содержимое репозитория.
2. Проверяет синтаксис `deploy/scripts/deploy.sh` командой `bash -n`.
3. Генерирует временные случайные значения пароля PostgreSQL и JWT-секрета.
4. Создаёт файл `deploy/.env.rehearsal` с правами `0600`.
5. Формирует ссылку на выбранный API-образ: `ghcr.io/andewaksar/todo-application-api:<image-tag>`.
6. Запускает `deploy/scripts/deploy.sh`.
7. Ожидает готовности сервисов не более 120 секунд.
8. Проверяет API через `http://127.0.0.1/health`.
9. Независимо от результата останавливает контейнеры и удаляет временные тома.

Одновременно допускается только один запуск `Deploy rehearsal`. Новый запуск не отменяет уже выполняющийся.

### Назначение проверки

Rehearsal проверяет, что опубликованный API-образ можно развернуть с помощью настоящих production-файлов:

- `deploy/compose.prod.yml`;
- `deploy/nginx/default.conf`;
- `deploy/scripts/deploy.sh`.

Таким образом проверяется тот же механизм, который используется при production-развёртывании, но без подключения к VDS и без использования production-секретов.

### Состав пробного контура

Пробное развёртывание повторяет текущий production-контур и включает:

- PostgreSQL;
- миграции Alembic;
- API;
- Nginx.

Kafka, ZooKeeper, scheduler и mailer в текущий production-контур не входят. Они проверяются отдельно в `docker-smoke` как часть полного локального контура разработки.

## Production-развёртывание

Workflow production-развёртывания расположен в `.github/workflows/deploy-production.yml`.

Он запускается вручную через GitHub Actions и принимает параметр `image_tag`. Необходимо указывать полный 40-символьный SHA коммита, образ которого уже опубликован в GHCR.

Workflow использует GitHub Environment `production` и разрешает запуск только из ветки `main`.

Одновременно может выполняться только одно production-развёртывание. Новый запуск не отменяет уже выполняющийся.

### Последовательность выполнения

Workflow выполняет следующие действия:

1. Загружает содержимое репозитория.
2. Проверяет, что запуск выполнен из ветки `main`.
3. Проверяет, что `image_tag` является полным 40-символьным SHA в нижнем регистре.
4. Создаёт временные SSH-файлы на GitHub runner.
5. Загружает приватный ключ из GitHub Environment secret.
6. Загружает доверенный SSH host key из `known_hosts`.
7. Проверяет корректность приватного SSH-ключа.
8. Подключается к VDS и проверяет:
   - наличие Docker;
   - наличие каталога `/opt/todo-application`;
   - доступность серверного файла `.env`.
9. Создаёт на сервере временный staging-каталог.
10. Передаёт на сервер:
    - `deploy/compose.prod.yml`;
    - `deploy/nginx/default.conf`;
    - `deploy/scripts/deploy.sh`.
11. Проверяет наличие переданных файлов и синтаксис `deploy.sh`.
12. Устанавливает файлы в `/opt/todo-application` с ограниченными правами доступа.
13. Формирует имя выбранного API-образа: `ghcr.io/andewaksar/todo-application-api:<image-tag>`.
14. Запускает `/opt/todo-application/scripts/deploy.sh`.
15. Ограничивает продолжительность удалённого развёртывания пятнадцатью минутами.
16. Проверяет публичный health endpoint.
17. Независимо от результата удаляет временный приватный ключ и файл `known_hosts` с GitHub runner.

### Передача deployment-файлов

Файлы не устанавливаются непосредственно в рабочий каталог приложения.

Сначала они загружаются во временный каталог вида `.incoming-<run-id>-<attempt>`. После проверки файлы переносятся в рабочие пути:

- Compose-конфигурация — `/opt/todo-application/compose.prod.yml`;
- конфигурация Nginx — `/opt/todo-application/nginx/default.conf`;
- deployment-скрипт — `/opt/todo-application/scripts/deploy.sh`.

После успешной установки временный каталог удаляется.

Такой порядок уменьшает риск частично обновлённой конфигурации при ошибке передачи файлов.

### GitHub Environment secrets

Environment `production` должен содержать следующие secrets:

- `DEPLOY_HOST` — IP-адрес или доменное имя VDS;
- `DEPLOY_PORT` — SSH-порт;
- `DEPLOY_USER` — отдельный пользователь развёртывания;
- `DEPLOY_SSH_KEY` — приватный SSH-ключ GitHub Actions;
- `DEPLOY_KNOWN_HOSTS` — проверенная запись SSH host key сервера;
- `PRODUCTION_HEALTH_URL` — публичный URL health endpoint.

Значения этих secrets запрещено сохранять в Git, выводить в документации или передавать через обычные переменные репозитория.

### Проверка подлинности сервера

Workflow использует `StrictHostKeyChecking=yes` и доверяет только записи из `DEPLOY_KNOWN_HOSTS`.

Перед добавлением нового VDS его SSH fingerprint необходимо получить непосредственно на сервере и отдельно сравнить с результатом `ssh-keyscan`. Нельзя без проверки копировать результат `ssh-keyscan` в GitHub Secrets: это лишает проверку сервера смысла.

### Публичная проверка

После завершения deployment-скрипта workflow выполняет HTTP-запрос к адресу из `PRODUCTION_HEALTH_URL`.

Проверка считается успешной, только если endpoint отвечает без HTTP-ошибки. Для временных сетевых сбоев используются повторные попытки подключения.

Успешный SSH-запуск ещё не означает успешное развёртывание. Окончательным подтверждением считается доступность приложения через публичный Nginx endpoint.

### Текущее состояние

Production workflow подготовлен и объединён с `main`, однако не должен запускаться до подготовки подходящего VDS и актуализации всех secrets окружения `production`.

Старые SSH-ключи, адрес сервера и `known_hosts` нельзя автоматически переносить на новый VDS. Для новой машины необходимо заново создать или установить deployment-ключ, проверить fingerprint и обновить GitHub Environment secrets.

## Deployment-скрипт

Сценарий развёртывания расположен в `deploy/scripts/deploy.sh`.

Один и тот же скрипт используется:

- в workflow `Deploy rehearsal` на временном GitHub runner;
- в workflow `Deploy production` на VDS;
- при необходимости — для ручного запуска.

Скрипт запускается в строгом режиме Bash через `set -Eeuo pipefail`. Он останавливает выполнение при ошибке команды, обращении к неопределённой переменной или ошибке внутри конвейера команд.

### Настраиваемые параметры

Скрипт поддерживает следующие переменные окружения:

- `COMPOSE_FILE` — путь к Compose-файлу; по умолчанию `deploy/compose.prod.yml`;
- `ENV_FILE` — путь к файлу переменных; по умолчанию `deploy/.env`;
- `HEALTH_URL` — адрес итоговой проверки приложения; по умолчанию `http://127.0.0.1/health`;
- `WAIT_TIMEOUT` — максимальное ожидание готовности Compose-сервисов в секундах; по умолчанию `120`.

Если переменные не заданы, используются значения для обычного production-развёртывания.

### Последовательность развёртывания

Deployment-скрипт выполняет следующие действия:

1. Определяет абсолютные пути к каталогу `deploy`, Compose-файлу и `.env`.
2. Проверяет наличие команд `docker` и `curl`.
3. Проверяет доступность Compose-файла и файла переменных.
4. Проверяет итоговую Compose-конфигурацию командой `docker compose config --quiet`.
5. Скачивает образы PostgreSQL, API и Nginx.
6. Запускает PostgreSQL и ожидает состояния `healthy`.
7. Запускает одноразовый сервис `migrate`.
8. Применяет Alembic-миграции до актуальной ревизии `head`.
9. После успешных миграций запускает API и Nginx.
10. Ожидает готовности API и Nginx.
11. Удаляет контейнеры, отсутствующие в текущей Compose-конфигурации, через `--remove-orphans`.
12. Проверяет приложение запросом к `HEALTH_URL`.
13. Выводит итоговое состояние Compose-сервисов.
14. Завершает работу только после успешного прохождения всех проверок.

API и Nginx не запускаются, если PostgreSQL не стал готовым или миграции завершились ошибкой.

### Диагностика ошибки

При ошибке скрипт автоматически:

1. сохраняет исходный код завершения;
2. выводит сообщение о неуспешном развёртывании;
3. показывает состояние Compose-сервисов;
4. выводит последние 100 строк логов PostgreSQL, API и Nginx;
5. завершает работу с исходным ненулевым кодом.

Диагностические команды ограничены таймаутом в 15 секунд и не должны скрывать первоначальную ошибку.

Скрипт не выполняет автоматический откат базы данных или предыдущего API-образа. Ошибка после успешного применения миграций может означать, что схема базы уже изменилась, даже если новая версия API не запустилась.

## Production Compose

Production-конфигурация расположена в `deploy/compose.prod.yml` и имеет имя проекта `todo-app-prod`.

Она не собирает приложение на сервере через `build`. API и миграции запускаются из готового образа, указанного в переменной `API_IMAGE`.

### Сервис `postgres`

Сервис использует образ `postgres:16-alpine`.

Для запуска обязательны:

- `POSTGRES_DB`;
- `POSTGRES_USER`;
- `POSTGRES_PASSWORD`.

Данные PostgreSQL сохраняются в именованном томе `postgres_data`. Пересоздание контейнера не удаляет базу данных, пока явно не удалён сам том.

PostgreSQL доступен только внутри Compose-сети. Порт `5432` не публикуется на хосте и не доступен напрямую из интернета.

Для текущего малоресурсного контура установлены ограничения:

- `shared_buffers=32MB`;
- `max_connections=20`;
- `work_mem=1MB`;
- `maintenance_work_mem=16MB`;
- лимит памяти контейнера `128m`;
- размер shared memory `32m`.

Healthcheck использует `pg_isready` и проверяет готовность указанной базы данных принимать подключения.

### Сервис `migrate`

Сервис `migrate` использует тот же образ `API_IMAGE`, что и основной API, но заменяет стандартную команду запуска приложения на `alembic upgrade head`.

Он:

- зависит от готовности PostgreSQL;
- получает `DATABASE_URL`;
- подключается к внутренней сети `backend`;
- запускается как одноразовый контейнер;
- удаляется после выполнения;
- имеет лимит памяти `160m`.

Сервис находится в профиле `tools` и не запускается при обычной команде `docker compose up`. Deployment-скрипт вызывает его отдельно с профилем `tools`.

### Сервис `api`

Сервис `api` запускает стандартную команду API-образа — Uvicorn.

Для запуска используются:

- `DATABASE_URL`;
- `JWT_SECRET_KEY`;
- `JWT_ALGORITHM`;
- `JWT_EXPIRES_MINUTES`.

`DATABASE_URL` и `JWT_SECRET_KEY` обязательны. Для алгоритма и срока действия токена предусмотрены значения по умолчанию.

API запускается только после перехода PostgreSQL в состояние `healthy`. Его собственный healthcheck обращается к `http://localhost:8000/health`.

Порт API не публикуется на хосте. К нему может обращаться Nginx через внутреннюю Compose-сеть.

Сервис имеет лимит памяти `160m` и политику перезапуска `unless-stopped`.

### Сервис `nginx`

Nginx использует образ `nginx:1.27-alpine`.

Он:

- запускается только после перехода API в состояние `healthy`;
- публикует порт `80` хоста;
- получает конфигурацию из `deploy/nginx/default.conf`;
- монтирует конфигурацию только для чтения;
- проверяет собственное состояние через `/nginx-health`;
- перенаправляет прикладные запросы в API;
- имеет лимит памяти `32m`;
- использует политику перезапуска `unless-stopped`.

Nginx является единственной публичной точкой входа в текущий production-контур.

### Сеть и постоянные данные

Все сервисы подключены к внутренней сети `backend`.

Внешнему клиенту доступен только Nginx через порт `80`. PostgreSQL и API не публикуют свои порты на хосте.

Именованный том `postgres_data` содержит постоянные данные базы. Обычное пересоздание контейнеров сохраняет этот том. Команда `docker compose down --volumes` удаляет том и данные базы, поэтому в production её нельзя выполнять без осознанного решения и актуальной резервной копии.

### Ограничения текущего контура

Production Compose включает только:

- PostgreSQL;
- одноразовые миграции;
- API;
- Nginx.

Kafka, ZooKeeper, scheduler и mailer отсутствуют намеренно. Для их добавления потребуется расширить production Compose, определить отдельные образы, переменные окружения, healthcheck, постоянные тома и ресурсные лимиты.

Совокупные лимиты контейнеров текущего контура составляют около 480 MiB без учёта Docker daemon, операционной системы и файлового кеша. Поэтому VDS с объёмом памяти около 512 MiB для такого запуска непригоден либо крайне нестабилен.

## Переменные окружения

Шаблон production-переменных расположен в `deploy/.env.example`.

Для реального запуска необходимо создать отдельный файл `deploy/.env` или `/opt/todo-application/.env` на VDS. Настоящий `.env` не должен добавляться в Git.

### `API_IMAGE`

Полное имя запускаемого API-образа:

`ghcr.io/andewaksar/todo-application-api:<full-commit-sha>`

Тег должен указывать на конкретный образ, ранее опубликованный CI в GHCR. Использование полного SHA делает развёртывание воспроизводимым и позволяет определить, какой именно код запущен.

### `POSTGRES_DB`

Название базы данных PostgreSQL.

Это значение используется:

- при первоначальном создании базы;
- healthcheck PostgreSQL;
- в строке подключения `DATABASE_URL`.

Название базы в `POSTGRES_DB` и `DATABASE_URL` должно совпадать.

### `POSTGRES_USER`

Имя пользователя PostgreSQL.

Это значение используется:

- при первоначальном создании пользователя;
- healthcheck PostgreSQL;
- в строке подключения `DATABASE_URL`.

Имя пользователя в `POSTGRES_USER` и `DATABASE_URL` должно совпадать.

### `POSTGRES_PASSWORD`

Пароль пользователя PostgreSQL.

Это секретное значение. Для production необходимо использовать длинный случайный пароль, не совпадающий с паролями других систем.

Пароль из `POSTGRES_PASSWORD` должен совпадать с паролем внутри `DATABASE_URL`. Иначе PostgreSQL запустится, но миграции и API не смогут подключиться к базе данных.

Если пароль содержит символы, имеющие специальное значение в URL, их необходимо percent-encode при добавлении в `DATABASE_URL`. Практичный вариант — генерировать пароль из безопасного набора символов, например в шестнадцатеричном формате.

### `DATABASE_URL`

Полная строка подключения API и Alembic к PostgreSQL.

Она имеет структуру:

`postgresql+asyncpg://<user>:<password>@postgres:5432/<database>`

Здесь:

- `postgresql+asyncpg` — PostgreSQL с асинхронным драйвером `asyncpg`;
- `<user>` — значение `POSTGRES_USER`;
- `<password>` — значение `POSTGRES_PASSWORD`;
- `postgres` — DNS-имя сервиса внутри Compose-сети;
- `5432` — внутренний порт PostgreSQL;
- `<database>` — значение `POSTGRES_DB`.

Вместо `localhost` используется имя `postgres`, потому что API подключается к базе из другого контейнера.

`DATABASE_URL` содержит пароль и является секретом.

### `JWT_SECRET_KEY`

Секретный ключ для подписи и проверки JWT.

Для production необходимо использовать длинное случайное значение. Слабый или раскрытый ключ позволяет подделывать токены авторизации.

При изменении `JWT_SECRET_KEY` ранее выпущенные токены перестают проходить проверку.

### `JWT_ALGORITHM`

Алгоритм подписи JWT.

По умолчанию используется `HS256`. Изменять алгоритм без одновременного изменения логики создания и проверки токенов нельзя.

Это значение не является секретом.

### `JWT_EXPIRES_MINUTES`

Срок действия access token в минутах.

По умолчанию используется значение `30`. Это значение не является секретом.

### Секретные и несекретные значения

Секретными являются:

- `POSTGRES_PASSWORD`;
- `DATABASE_URL`;
- `JWT_SECRET_KEY`.

Условно несекретными являются:

- `API_IMAGE`;
- `POSTGRES_DB`;
- `POSTGRES_USER`;
- `JWT_ALGORITHM`;
- `JWT_EXPIRES_MINUTES`.

Даже несекретные production-настройки рекомендуется хранить в серверном `.env`, чтобы конфигурация конкретного окружения не смешивалась с кодом.

На сервере `.env` должен принадлежать пользователю `deploy` и иметь права `0600`.

## Конфигурация Nginx

Production-конфигурация Nginx расположена в `deploy/nginx/default.conf`.

Nginx является единственной публичной точкой входа в приложение. Он принимает HTTP-запросы на порту `80` и передаёт прикладные запросы контейнеру API.

### Endpoint `/nginx-health`

Endpoint `/nginx-health` проверяет только сам Nginx.

Он возвращает `200 OK` и текст `ok`, не обращаясь к API или PostgreSQL. Логирование запросов к этому endpoint отключено, чтобы периодические healthcheck не засоряли access log.

Успешный ответ `/nginx-health` означает:

- контейнер Nginx запущен;
- Nginx загрузил конфигурацию;
- HTTP-сервер принимает запросы.

Он не подтверждает работоспособность API или базы данных.

### Endpoint `/health`

Запрос к `/health` проходит через Nginx и перенаправляется в API.

Успешный ответ означает, что:

- Nginx принимает запросы;
- внутренняя Compose-сеть работает;
- имя сервиса `api` разрешается;
- API слушает порт `8000`;
- endpoint приложения отвечает без HTTP-ошибки.

Поэтому `/health` используется как итоговая проверка развёртывания.

Текущая проверка `/health` не обязательно подтверждает выполнение реального запроса к PostgreSQL. Если требуется проверять также базу данных, необходимо отдельно реализовать readiness endpoint с проверкой подключения к БД.

### Проксирование запросов

Все запросы, кроме точного `/nginx-health`, обрабатываются блоком `location /` и передаются по адресу:

`http://api:8000`

Имя `api` является DNS-именем Compose-сервиса во внутренней сети `backend`. Порт API не публикуется на хосте.

Для проксирования используется HTTP/1.1.

### Передаваемые заголовки

Nginx передаёт API следующие заголовки:

- `Host` — исходное имя хоста, указанное клиентом;
- `X-Real-IP` — IP-адрес клиента, подключившегося к Nginx;
- `X-Forwarded-For` — цепочка прокси и исходный IP клиента;
- `X-Forwarded-Proto` — исходный протокол запроса, например `http` или `https`.

Эти заголовки нужны приложению для корректного определения исходного адреса клиента, протокола и домена.

API не должно безусловно доверять forwarded-заголовкам, если запрос способен попасть к нему в обход доверенного Nginx. В текущей конфигурации порт API наружу не опубликован, что уменьшает этот риск.

### Таймауты прокси

Настроены следующие таймауты:

- `proxy_connect_timeout 5s` — время на установление соединения с API;
- `proxy_send_timeout 30s` — допустимое время передачи запроса в API;
- `proxy_read_timeout 30s` — допустимое ожидание ответа от API.

Если API не принимает соединение или слишком долго не отвечает, Nginx завершает запрос ошибкой, не удерживая соединение бесконечно.

### Дополнительные настройки

Директива `server_name _` используется как универсальный сервер по умолчанию до настройки отдельного доменного имени.

Директива `server_tokens off` скрывает точную версию Nginx из стандартных HTTP-ответов. Это уменьшает объём технической информации, доступной внешнему клиенту, но само по себе не заменяет своевременное обновление образа Nginx.

## Как найти опубликованный образ

После успешного объединения Pull Request с `main` workflow `CI` выполняет проверки и запускает job `Publish API image`.

Чтобы найти тег образа:

1. Открыть репозиторий в GitHub.
2. Перейти в `Actions`.
3. Открыть успешный запуск workflow `CI` для нужного коммита в `main`.
4. Убедиться, что job `Publish API image` завершился успешно.
5. Открыть пакет `todo-application-api` в разделе Packages.
6. Скопировать полный SHA-тег нужной версии.

Также полный SHA текущего коммита можно получить локально командой `git rev-parse HEAD`, но использовать его для развёртывания можно только после подтверждения, что соответствующий образ действительно опубликован в GHCR.

Тег не должен содержать имя образа или команду `docker pull`. В поле `image_tag` передаётся только 40-символьный SHA.

## Запуск пробного развёртывания

Перед production-развёртыванием рекомендуется проверить выбранный образ через `Deploy rehearsal`.

Порядок запуска:

1. Открыть вкладку `Actions`.
2. Выбрать workflow `Deploy rehearsal`.
3. Нажать `Run workflow`.
4. Выбрать ветку `main`.
5. Вставить полный SHA в поле `API image tag from GHCR`.
6. Запустить workflow.
7. Открыть job `Rehearse production deployment` и дождаться завершения всех шагов.

Проверка успешна, если:

- production Compose прошёл валидацию;
- все необходимые образы скачались;
- PostgreSQL стал `healthy`;
- Alembic-миграции завершились с кодом `0`;
- API и Nginx стали `healthy`;
- запрос к `/health` завершился успешно;
- workflow имеет статус `Success`.

Успешный rehearsal подтверждает работоспособность образа и deployment-механизма на чистом временном окружении. Он не проверяет SSH-доступ, состояние VDS, серверный `.env` и реальные production-данные.

## Запуск production-развёртывания

Production-развёртывание допускается только после успешных CI и rehearsal для того же SHA.

Перед запуском необходимо убедиться, что:

- VDS подготовлен;
- GitHub Environment `production` содержит актуальные secrets;
- серверный `/opt/todo-application/.env` существует и доступен пользователю `deploy`;
- SSH fingerprint проверен;
- выбранный образ опубликован в GHCR;
- имеется актуальная резервная копия базы данных;
- миграции проверены на совместимость с текущей версией приложения.

Порядок запуска:

1. Открыть вкладку `Actions`.
2. Выбрать workflow `Deploy production`.
3. Нажать `Run workflow`.
4. Выбрать ветку `main`.
5. Вставить полный SHA проверенного образа.
6. Запустить workflow.
7. При наличии protection rules подтвердить deployment в Environment `production`.
8. Наблюдать выполнение всех шагов до итогового healthcheck.

Нельзя запускать production workflow с SHA, который не прошёл CI или rehearsal.

## Проверка после развёртывания

После успешного workflow необходимо проверить приложение независимо от GitHub Actions.

Публичные проверки:

- `curl --fail --show-error http://<host>/nginx-health`;
- `curl --fail --show-error http://<host>/health`.

Проверки на сервере выполняются от пользователя `deploy` из каталога `/opt/todo-application`:

- `docker compose --env-file .env -f compose.prod.yml ps`;
- `docker compose --env-file .env -f compose.prod.yml logs --tail=100 api`;
- `docker compose --env-file .env -f compose.prod.yml logs --tail=100 nginx`;
- `docker compose --env-file .env -f compose.prod.yml logs --tail=100 postgres`.

Ожидаемое состояние:

- PostgreSQL — `healthy`;
- API — `healthy`;
- Nginx — `healthy`;
- сервис `migrate` отсутствует, поскольку это одноразовый контейнер;
- наружу опубликован только порт Nginx;
- оба HTTP endpoint возвращают успешный ответ.

## Диагностика типовых ошибок

### Образ не найден

Признаки:

- ошибка на шаге `Pulling production images`;
- сообщение `manifest unknown`, `not found` или `pull access denied`.

Проверить:

- полный SHA без лишних символов;
- наличие версии в GHCR;
- успешность job `Publish API image`;
- доступность пакета для Docker daemon на VDS.

Нельзя заменять отсутствующий SHA на `latest`: это уничтожает воспроизводимость развёртывания и скрывает реальную причину ошибки.

### SSH-подключение не установлено

Признаки:

- `Permission denied`;
- `Host key verification failed`;
- timeout подключения.

Проверить:

- `DEPLOY_HOST`, `DEPLOY_PORT` и `DEPLOY_USER`;
- публичную часть deployment-ключа в `authorized_keys`;
- права на `.ssh` и `authorized_keys`;
- соответствие `DEPLOY_KNOWN_HOSTS` текущему host key сервера;
- firewall и доступность SSH-порта.

Нельзя отключать `StrictHostKeyChecking` для обхода ошибки. Сначала необходимо установить причину изменения host key.

### PostgreSQL не стал `healthy`

Проверить:

- логи контейнера PostgreSQL;
- значения `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD`;
- свободное место на диске;
- доступную память;
- состояние тома `postgres_data`.

Нельзя удалять `postgres_data` как способ «починить запуск»: это удалит данные production-базы.

### Миграции завершились ошибкой

Проверить:

- логи контейнера `migrate`;
- соответствие `DATABASE_URL` параметрам PostgreSQL;
- текущую Alembic-ревизию;
- журнал миграций;
- совместимость миграции с существующими данными.

Не следует повторять миграцию вслепую. Сначала нужно определить, была ли транзакция полностью отменена или схема изменилась частично.

### API не стал `healthy`

Проверить:

- логи API;
- `DATABASE_URL`;
- `JWT_SECRET_KEY`;
- результат миграций;
- доступную память;
- ответ внутреннего endpoint `/health`.

Если API завершается из-за нехватки памяти, увеличение restart-политики не решает проблему и может создать бесконечный цикл перезапусков.

### Nginx не стал `healthy`

Проверить:

- логи Nginx;
- наличие `/opt/todo-application/nginx/default.conf`;
- синтаксис конфигурации;
- состояние API;
- занятость порта `80`;
- ответ `/nginx-health` внутри контейнера.

Успешный `/nginx-health` при ошибке `/health` обычно означает, что Nginx работает, но API недоступен или отвечает с ошибкой.

### Публичный healthcheck завершился ошибкой

Проверить:

- доступность порта `80` или `443`;
- firewall;
- DNS;
- состояние Nginx и API;
- правильность `PRODUCTION_HEALTH_URL`;
- маршрутизацию внешнего трафика.

Успешные контейнерные healthcheck не гарантируют доступность приложения из интернета.
