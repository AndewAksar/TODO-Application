# JWT Debugging Runbook

## 1. Назначение

Пошаговая диагностика проблем с JWT и `get_current_user`.

Цель:
* детерминированно находить причину `401 Unauthorized`
* исключить dependency-bug в auth-цепочке

Типовые сценарии:
* `401` всегда
* `401` только в Docker / CI
* токен создаётся, но `/me` не работает
* токен валидный, но пользователь не найден
* «случайные» `401` (время, таймзона, `exp`)

---

## 2. Типовые симптомы

* `401 Unauthorized` на всех запросах
* `401` только в контейнере или CI
* `/login` работает, `/me` — нет
* `sub` корректный, но user отсутствует
* нестабильные `401` (обычно проблема времени)

---

## 3. Диагностика (строгий порядок)

### Шаг A — Проверка конфигурации

Проверить:
* `JWT_SECRET_KEY` задан и не пустой
* `JWT_ALGORITHM` совпадает в `encode` и `decode`
* `JWT_EXPIRES_MINUTES` адекватный

Типовые ошибки:
* секрет пустой → токены не должны выпускаться
* разные секреты в разных окружениях
* несовпадение алгоритма

---

### Шаг B — Проверка заголовка

Ожидаемый формат:
`Authorization: Bearer <token>`


Типовые ошибки клиента:
* `Token <token>`
* `bearer<token>` (без пробела)
* токен передан в query или body

---

### Шаг C — Проверка decode-инвариантов

Инварианты:
* token не пустой
* подпись проверяется
* `exp` проверяется
* `iat` присутствует и валиден
* `sub` — строка цифр
* `sub` преобразуется в `int(user_id)`

Любое нарушение → `401 Unauthorized`.

---

### Шаг D — Проверка DB-сверки пользователя

Проверить:
* `repo.get_by_id(user_id)` ищет по корректному полю
* пользователь реально существует
* транзакция `commit()` выполнена после регистрации
* Если при `repo.get_by_id(...)` возникает ошибка БД/соединения/таймаут:
  - это не проблема токена,
  - ожидаемый ответ сервиса: `503 Service Unavailable` (без деталей),

причина фиксируется только в логах (без токена/Authorization).
---

### Шаг E — Проверка dependency-bug

Проверить:
* эндпоинт защищён:
  * либо `Depends(get_current_user)`
  * либо router-level dependency

`get_current_user` обязан:
* **никогда** не возвращать `None`
* при любой ошибке кидать `HTTPException(401)`
* не раскрывать причину ошибки

Деталь ошибки:
* всегда одинаковая (`"Unauthorized"`)

---

## 4. Минимальный набор тестов (контракт)

Обязательные кейсы:
* без токена → `401`
* мусорный токен → `401`
* `exp` в прошлом → `401`
* валидный `sub`, но user отсутствует → `401`
* валидный токен + user существует → `200`
* при недоступной БД → `503`

Если хотя бы одного теста нет — защита неполная.

---

## 5. Если «работает локально, падает в CI»

Проверить:
* `JWT_SECRET_KEY` задан в CI
* время используется в UTC
* `iat` и `exp` генерируются в UTC
* тестовая БД не пересоздаётся между шагами

---

## 6. Логирование (без утечек)

Разрешено логировать:
* факт `401`
* категорию ошибки:
  * `missing auth header`
  * `invalid format`
  * `token invalid`

Запрещено логировать:
* JWT-токен
* JWT-секрет
* полный `Authorization` header

Логирование должно соответствовать требованиям OBSERVABILITY.md и SECURITY_POLICY.md.
